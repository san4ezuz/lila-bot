# UX-итерация 1 — план изменений по итогам первого живого теста

Статус: решения приняты, в реализации
Дата: 2026-08-27
Контекст: обратная связь после первого прогона бота в Telegram (см. чат). Решения по пунктам
зафиксированы пользователем, здесь — как их реализовать.

Решено: П1 (длина текста) и П3 (лимит ходов) — **не трогаем в этой итерации**. Ниже — только
П2, П4, П5, П6 и замена входа через `/start`.

---

## 1. Убрать счётчик ходов из прогресс-строки (П2)

**Сейчас:** `PROGRESS_LINE = "Клетка {position} · ход {turn} из {turn_limit}"` — показывает
и позицию, и номер хода из лимита, создавая ощущение гонки на время.

**Меняем на:** только номер и название клетки. Лимит ходов остаётся внутренней механикой
(защита от бесконечной партии), пользователю не показывается вообще.

### Изменения в коде

- `src/bot/texts.py`: `PROGRESS_LINE` → что-то вроде `"📍 Клетка {position} — {cell_name}"`
  (нужно название клетки, не только номер — см. также П6 ниже).
- `src/bot/handlers/game.py::on_roll`: сейчас progress строится из `result.position` +
  `settings.turn_limit` — нужно передавать `result.cell.name` вместо лимита. `RollResponse`
  уже содержит `cell: CellOut | None` с `name`, менять API не придётся.
- Проверить `src/api/schemas.py::RollResponse` — поле `turn` в контракте API можно оставить
  (для будущей Mini App / аналитики это полезно), просто бот перестаёт его **показывать**
  игроку. Контракт API не меняем, меняем только рендер в боте.

**Не меняется:** `src/core/rules.py`, `turn_limit` в БД/конфиге, метрики — там `turn` как был
служебным полем, так и остаётся.

## 2. Мягкие напоминания о незавершённой партии (П4)

**Требование:** не быть навязчивым. Каскад: **через 24ч → через 3 дня → через 7 дней**, разный
тон на каждом шаге (первое — мягкое, третье — «дверь открыта, без давления»). После третьего —
молчим. Дать возможность **отложить** («напомнить позже») и **отказаться** («больше не
напоминать») прямо из сообщения-напоминания.

### Модель данных

**Важно:** `games.updated_at` уже используется как якорь и для этой фичи, и для
`abandon_stale_games` (48ч), и у него `onupdate=func.now()` — любой `UPDATE` строки `games`
(даже если меняется только несвязанное поле) сдвигает `updated_at` на текущий момент. Если
хранить `reminder_stage` прямо в `games`, то после отправки первого напоминания и записи
`reminder_stage=1` в ту же строку `updated_at` сам сдвинется на «сейчас» — и порог для
следующего напоминания начнёт отсчитываться заново от момента отправки, а не от реальной
последней активности игрока. Каскад 24ч/3д/7д тем самым сломается (и заодно собьётся
`abandon_stale`, который тоже смотрит на `updated_at`).

**Решение:** трекинг напоминаний — **отдельная таблица**, не колонки в `games`:

```sql
reminders (
  game_id           uuid pk references games(id),
  stage             int default 0,           -- 0..3
  snoozed_until     timestamptz null,
  created_at        timestamptz default now(),
  updated_at        timestamptz default now()  -- свой собственный updated_at, не трогает games
)
```

Плюс `users.reminders_opt_out: bool default false` — на **пользователе**, а не на партии:
если игрок один раз сказал «не напоминай», это действует на все его будущие незавершённые
партии, а не только на текущую.

### Логика (новый крон-скрипт, по аналогии с `scripts/abandon_stale_games.py`)

`scripts/send_reminders.py`, запускается почаще, чем abandon-стейл — например, **раз в час**
(конкретные пороги 24ч/3д/7д не требуют более частого опроса, но часовая гранулярность даёт
предсказуемое время доставки без сложного планирования).

Для каждой партии в статусе `active`/`setup`, где `updated_at` (или отдельная метка последнего
напоминания) старше нужного порога, `reminder_stage` соответствует следующему шагу, пользователь
не в `reminders_opt_out`, и (если есть) `reminder_snoozed_until` уже прошёл:

| stage | порог бездействия от `updated_at` | тон |
|---|---|---|
| 0→1 | 24 часа | мягкое: «твоя партия ждёт, если будет минутка» |
| 1→2 | 3 дня | нейтральное, без давления: короткое напоминание + цитата вопроса, на котором остановились |
| 2→3 | 7 дней | последнее, тёплое: «путь никуда не делся, вернёшься — начнём с того же места», после него `reminder_stage` фиксируется на 3 и больше не проверяется |

**Решено:** пороги считаются от `updated_at` (последняя активность), не от `created_at`.
Это не «стакается» до 11 дней, как я предполагал в черновике: `updated_at` — фиксированная
точка отсчёта, которая не двигается, пока игрок не вернётся, так что 24ч/3д/7д — это три
проверки одного и того же неподвижного якоря, а не последовательные интервалы друг от друга.

Сообщение — `notify_user()` из `src/services/billing_service.py` (уже есть, raw Bot API,
best-effort) — можно вынести в общий `src/services/notify.py`, чтобы не тянуть импорт из
billing в напоминания.

### Кнопки в сообщении-напоминании

`InlineKeyboardMarkup`:
- **«Продолжить партию»** → deep-link или просто напоминание, что можно написать боту;
  по нажатию — вызвать `/game/{id}` и показать текущее состояние + кнопку «Бросить кубик»
- **«Напомнить позже»** → `callback_data="snooze_reminder:{game_id}"`, ставит
  `reminder_snoozed_until = now + 24h` (или предложить выбор «через 3 дня» / «через неделю» —
  можно упростить до одного варианta «+3 дня» на первой итерации)
- **«Больше не напоминать»** → `callback_data="opt_out_reminders"`, ставит
  `users.reminders_opt_out = true`. Если игрок потом начнёт новую партию — уместно один раз
  ненавязчиво предложить снова включить напоминания (не обязательно в этой итерации)

### Новые API-эндпоинты

- `POST /users/{telegram_id}/reminders/opt-out`
- `POST /game/{id}/reminders/snooze` (body: `{hours: int}` или фиксированный шаг)

Оба — тонкие, только апдейт БД, без LLM.

### Открытый вопрос

Считать ли пороги от **старта партии** (created_at) или от **последней активности**
(updated_at)? Предлагаю от старта партии — иначе игрок, который зашёл на секунду и опять
пропал, будет получать напоминания заново от каждого мелкого действия, программа растянется
непредсказуемо. `updated_at` уже занят под `game_abandoned` (48ч), у напоминаний — своя
временная база от `created_at`.

## 3. Вступление / описание игры (П5)

**Задача:** первое сообщение короче, подробности — по запросу, не перегружая первый экран.

### Реализация

- `/start` (и новый flow ниже) шлёт **короткое** приветствие (1-2 предложения, не текущий
  длинный WELCOME) + две кнопки: **«🎲 Начать партию»** и **«ℹ️ Что это за игра?»**
- Кнопка «Что это за игра?» → разворачивает подробное описание: что такое Лила, как проходит
  партия, сколько занимает времени, чего не стоит ожидать (не терапия, не гадание), опционально
  дисклеймер про safety-ветку. Через `callback_data="about_game"`
- Технически: `<blockquote expandable>` (Telegram HTML) — сворачиваемый блок прямо в сообщении,
  можно использовать вместо отдельного экрана, если хочется избежать лишнего сообщения
  (`aiogram` поддерживает HTML parse mode, который уже включён в `src/bot/main.py`
  через `DefaultBotProperties(parse_mode=ParseMode.HTML)`)
- `/help` — команда с тем же подробным текстом, для тех, кто ищет её отдельно от кнопки

### Новые файлы/правки

- `src/bot/texts.py`: `WELCOME_SHORT`, `ABOUT_GAME_TEXT`
- `src/bot/keyboards.py`: `start_game_kb()` — добавить вторую кнопку `about_game`
- `src/bot/handlers/start.py`: новый хендлер `on_about_game` (callback), команда `/help`

## 4. Визуальное оформление текста (П6)

- **Жирным** (`<b>...</b>`) — номер и название клетки, вынесенные отдельной строкой сверху
  каждого игрового сообщения (см. П2 — это тот же элемент, просто с форматированием)
- Точечные эмодзи-маркеры, не более 1-2 на сообщение:
  - 📍 — текущая клетка
  - 🎲 — результат броска (только в самом сообщении с числом, не в каждой строке)
  - ✨ — финиш партии
  - 🔗 / ⬆️ — попадание на стрелу
  - 🐍 / ⬇️ — попадание на змею (эмодзи змеи — по вкусу, может звучать негативно, можно
    заменить на нейтральный ⬇️/🔻)
- Формат одного игрового сообщения:
  ```
  📍 <b>Клетка 8 — Алчность</b>

  {текст интерпретации от LLM}
  ```
- Технически: раз используем HTML разметку, `guide.py`/`prompts.py` не должны просить модель
  генерировать markdown/HTML сама (риск сломать разметку) — оборачивание жирным и эмодзи делает
  **бот**, а не LLM, вокруг чистого текста ответа. Это не требует правки промпта.

## 5. Заменить обязательный `/start` на кнопку / автоматический старт

**Требование:** не заставлять печатать команду вручную.

### Что уже даёт Telegram «бесплатно»

Для совсем нового чата с ботом Telegram-клиент сам показывает кнопку **«Start»**
внизу экрана — она уже заменяет необходимость печатать `/start` руками. Переименовать
именно эту системную кнопку нельзя (это часть интерфейса Telegram, а не бота), но можно
дополнительно:

1. **Menu Button** (постоянная кнопка слева от поля ввода, видна всегда, не только в первом
   сообщении) — настраивается через Bot API `setChatMenuButton`, можно задать текст
   «🎲 Играть» вместо стандартного «Menu». Требует одного вызова при старте `src/bot/main.py`
   (`await bot.set_chat_menu_button(...)`), не требует изменения хендлеров.
2. **Подстраховка**: если пользователь всё-таки написал что-то текстом вместо нажатия кнопки
   (например «привет» или просто текст) и активной партии нет — не молчать, а показать то же
   приветствие с кнопкой «Начать партию», а не проваливаться в «текст без контекста». Сейчас
   `on_player_response` в этом случае просто ничего не делает
   (`if game_id is None: return`) — это и есть точка, которую стоит поправить.
3. Оставить `/start` рабочим как есть — как явный «сброс», это не помешает.

### Изменения в коде

- `src/bot/main.py`: один вызов `set_chat_menu_button` при старте (или через BotFather вручную
  один раз — тоже вариант, без кода вообще, но тогда придётся переделывать при смене текста)
- `src/bot/handlers/game.py::on_player_response`: если нет `game_id` в состоянии — вместо
  `return` показывать приветствие + кнопку «Начать партию» (тот же текст, что и `/start`)

## Порядок реализации (предложение)

Логичнее не по номерам пунктов, а по независимости кусков:

1. **П2 + П6 вместе** — это один и тот же кусок кода (`texts.py`, `on_roll` в `game.py`),
   рендер сообщений о ходах. Дешёво, без миграций.
2. **П5 + замена /start** — тоже чисто бот-слой, без миграций, без новых эндпоинтов.
3. **П4 (напоминания)** — самое трудоёмкое: миграция БД, новый крон-скрипт, два новых
   эндпоинта, новые кнопки/хендлеры. Имеет смысл делать последним и отдельно проверять
   живым прогоном (крон нельзя протестировать иначе, кроме как подождать реальное время или
   временно занизить пороги для проверки).
