# «Лила» — план разработки MVP Telegram-бота

Статус: черновик v1
Дата: 2026-08-26
Основано на: MVP-описание «Лила — трансформационная игра с LLM-проводником»

---

## 0. Что считаем результатом MVP

Работающий в проде Telegram-бот, в котором пользователь может:

1. Начать партию, сформулировать запрос.
2. Пройти партию до конца (бросок → клетка → интерпретация LLM → рефлексивный диалог → следующий бросок).
3. Получить связное резюме пути.
4. При попытке начать вторую партию — упереться в пейволл и оплатить через Tribute.

Технически: бэкенд **API-first** (FastAPI + Postgres), бот — **тонкий клиент** этого API (aiogram).
Mini App в MVP **не делается**, но добавляется потом как второй клиент к тому же API без переписывания бэкенда.

**Главное архитектурное правило проекта (нарушать нельзя):**
> В хендлерах aiogram нет игровой логики и нет вызовов LLM. Хендлер = «принял апдейт → дёрнул Game API → отрисовал ответ в Telegram».

## 1. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | Python 3.12 | общий для бота и API |
| API | FastAPI + Pydantic v2 | быстрый, типизированный, автодоки |
| Бот | aiogram 3.x | актуальный async-фреймворк |
| БД | PostgreSQL 16 | состояние партий, транзакции |
| ORM/миграции | SQLAlchemy 2.0 (async) + Alembic | стандарт |
| LLM | Anthropic Python SDK, модель `claude-opus-5` | качество интерпретаций критично для продукта |
| Оплата | Tribute (webhook) | по продуктовому решению |
| Хостинг | Railway (2 сервиса + Postgres) | быстро, дёшево на старте |
| Зависимости | uv (или Poetry) | скорость |
| Тесты | pytest + pytest-asyncio + httpx.AsyncClient | движок покрываем тестами обязательно |
| Логи | structlog (JSON) | нужно для разбора «плохих» партий |

**Про LLM (актуальные факты API):**

- Модель по умолчанию: `claude-opus-5` (контекст 1M, $5/$25 за 1M токенов вход/выход).
- Параметр `thinking: {"type": "adaptive"}` — включён по умолчанию у Opus 5; `budget_tokens` **удалён** (вернёт 400).
- Глубину и стоимость регулируем через `output_config: {"effort": "low" | "medium" | "high"}`.
  Для интерпретаций клеток начать с `medium`, для финального резюме — `high`.
- Prompt caching: `cache_control: {"type": "ephemeral"}` на статическом системном промпте.
  Минимальный кэшируемый префикс ~1024 токена; порядок рендера `tools → system → messages`,
  поэтому всё волатильное (текущий бросок, номер хода, время) — **после** последней точки кэша.
  Проверять кэш по `usage.cache_read_input_tokens` (должен быть > 0 со второго хода партии).
- Стриминг не нужен (Telegram всё равно шлёт сообщение целиком), но `max_tokens` держим
  осознанно низким — это часть контроля длины ответа.

## 4. Этап 1 — Формализация игрового поля (≈1–1.5 дня, продуктовая работа)

Самый недооценённый этап. Пока нет качественных данных по клеткам — LLM будет «лить воду».

### 4.1 Схема клетки (`data/board.json`)

```json
{
  "version": "1.0",
  "cells": [
    {
      "id": 1,
      "name": "Рождение",
      "guna": "tamas | rajas | sattva",
      "element": "земля | вода | огонь | воздух | эфир",
      "plane": 1,
      "theme": "короткая формулировка темы клетки, одно предложение",
      "keywords": ["...", "...", "..."],
      "facets": [
        "грань трактовки 1 — что клетка может значить",
        "грань трактовки 2 — другой ракурс",
        "грань трактовки 3 — теневой/ресурсный ракурс"
      ],
      "questions": [
        "рефлексивный вопрос 1",
        "рефлексивный вопрос 2",
        "рефлексивный вопрос 3"
      ]
    }
  ]
}
```

Требование: `facets` и `questions` — **фактура, а не готовый текст**. LLM использует их как опору,
но формулирует ответ в контексте запроса игрока. 3 грани + 3 вопроса на клетку × 72 — объём,
который лучше делать вместе с экспертом по игре, а не генерировать вслепую.

Практичный порядок: черновик генерируется LLM пачками по 8–12 клеток на основе классической
таблицы Лилы → эксперт вычитывает и правит → в репозиторий попадает уже вычитанное.

### 4.2 Переходы (`data/transitions.json`)

```json
{
  "arrows": { "10": 23, "17": 69, "20": 32 },
  "snakes": { "12": 8, "16": 4 }
}
```

### 4.3 `docs/RULES.md` — правила словами, до кода

Зафиксировать явно (значения ниже — предлагаемые дефолты, **подтвердить с экспертом**):

| Правило | Предлагаемый дефолт | Статус |
|---|---|---|
| Стартовая позиция | 68 «Космическое сознание», фишка вне игры | уточнить |
| Вход в игру | нужен бросок «6», после чего фишка встаёт на клетку 6 | уточнить |
| Финиш | ровно на 68; при перелёте фишка остаётся на месте | уточнить |
| Повторный бросок на «6» | да / нет | решить |
| Три «6» подряд | правило есть в классике — включаем? | решить |
| Клетки 69–72 | достижимы только по стреле | уточнить |
| Лимит ходов | 40 бросков → мягкое завершение с резюме | продуктовое решение |
| Лимит попыток входа | 6 неудачных бросков → подсказка проводника, не блокируем | предложение |

> Важно: в исходном MVP-описании клетка 68 названа и стартовой («Рождение»), и финальной
> («завершение партии — клетка 68»). В классической Лиле это одна и та же клетка (путь
> «из сознания в сознание»), но в текстах бота это надо развести словами, иначе игрок запутается.
> Решение принимается до кода, а не в коде.

**Готово когда:** `board.json` содержит 72 валидные клетки, `transitions.json` заполнен,
в `RULES.md` не осталось пунктов со статусом «уточнить».

### 4.4 Валидатор данных (`tests/test_board_data.py`)

- ровно 72 клетки, `id` от 1 до 72 без пропусков и дублей;
- у каждой клетки непустая `theme`, ≥2 `facets`, ≥2 `questions`;
- все `from` / `to` переходов в диапазоне 1..72;
- стрелы ведут вверх, змеи — вниз;
- нет клетки одновременно в `arrows` и `snakes`;
- нет цепочек переходов (после перехода новая клетка не является источником другого перехода) —
  либо цепочки разрешаются явно и покрываются отдельным тестом.

## 5. Этап 2 — Игровой движок (≈1 день)

Чистые функции: **без БД, без сети, без LLM**. Это то, что потом переиспользует и Mini App.

### 5.1 Доменные модели (`src/core/models.py`)

```python
@dataclass(frozen=True)
class GameState:
    position: int | None        # None = ещё не вошёл в игру
    in_play: bool
    turn: int
    finished: bool
    history: tuple[MoveRecord, ...]

@dataclass(frozen=True)
class MoveResult:
    roll: int
    from_position: int | None
    raw_position: int | None    # после броска, до стрелы/змеи
    final_position: int | None  # после перехода
    transition: Literal["arrow", "snake", None]
    event: Literal["not_entered", "entered", "moved", "blocked_overshoot", "finished"]
    extra_roll: bool
```

### 5.2 Функции (`src/core/rules.py`)

- `roll_dice(rng) -> int`
- `apply_roll(state, roll, board, transitions, config) -> tuple[GameState, MoveResult]`
- `is_finished(state) -> bool`

Всё детерминировано при заданном `roll` — это делает тесты тривиальными.

### 5.3 Тесты (`tests/test_rules.py`) — обязательный минимум

- не вошёл в игру, выпало 1–5 → позиция не меняется, `event="not_entered"`;
- выпало 6 → вход, `event="entered"`;
- обычный ход без перехода;
- попадание на стрелу → позиция = цель стрелы, `transition="arrow"`;
- попадание на змею → вниз;
- перелёт мимо 68 → `event="blocked_overshoot"`, позиция не меняется;
- точное попадание на 68 → `finished=True`;
- достижение лимита ходов → партия закрывается.

### 5.4 CLI-прогон (`scripts/play_cli.py`)

Прогнать 1000 случайных партий и собрать статистику: средняя длина партии, доля партий,
дошедших до 68 в пределах лимита ходов, доля партий, застрявших на входе.

**Это продуктовая проверка, а не техническая:** если 70% партий упираются в лимит ходов —
правило финиша или лимит надо менять до того, как к этому подключены LLM и деньги.

**Готово когда:** тесты зелёные, статистика по 1000 партий согласована с экспертом.

## 6. Этап 3 — Данные и БД (≈0.5–1 день)

### 6.1 Схема

```sql
users (
  id                    bigserial pk,
  telegram_id           bigint unique not null,
  username              text,
  first_name            text,
  created_at            timestamptz default now(),
  has_free_game_used    boolean default false,
  paid_games_available  int default 0
);

games (
  id            uuid pk,
  user_id       bigint fk -> users,
  status        text,          -- 'setup' | 'active' | 'finished' | 'abandoned'
  intention     text,          -- запрос игрока
  position      int,           -- null пока не вошёл в игру
  in_play       boolean default false,
  turn          int default 0,
  is_paid       boolean default false,
  board_version text,
  created_at    timestamptz,
  finished_at   timestamptz,
  summary       text
);

moves (
  id          bigserial pk,
  game_id     uuid fk -> games,
  turn        int,
  roll        int,
  from_pos    int,
  raw_pos     int,
  to_pos      int,
  transition  text,            -- 'arrow' | 'snake' | null
  event       text,
  created_at  timestamptz
);

messages (
  id          bigserial pk,
  game_id     uuid fk -> games,
  move_id     bigint fk -> moves null,
  role        text,            -- 'guide' | 'player'
  content     text,
  tokens_in   int,
  tokens_out  int,
  created_at  timestamptz
);

payments (
  id           bigserial pk,
  user_id      bigint fk -> users,
  provider     text default 'tribute',
  external_id  text unique,
  amount       numeric,
  currency     text,
  status       text,           -- 'pending' | 'paid' | 'failed'
  raw_payload  jsonb,
  created_at   timestamptz
);

events (                        -- аналитика
  id         bigserial pk,
  user_id    bigint,
  game_id    uuid,
  name       text,
  props      jsonb,
  created_at timestamptz
);
```

Индексы: `games(user_id, status)`, `moves(game_id, turn)`, `messages(game_id, id)`, `events(name, created_at)`.

### 6.2 Правила работы с состоянием

- Состояние партии — **только в Postgres**. Никакого in-memory кеша и никакого `FSMContext`
  aiogram для игровых данных (FSM — только для UI-шагов вроде «ждём текст запроса»).
- Один пользователь = максимум одна партия в статусе `active` (частичный уникальный индекс).
- `moves` + `messages` — одновременно лог для отладки тона, источник контекста для LLM
  и сырьё для метрик. Не экономить на записи.

**Готово когда:** миграция применяется, репозитории покрыты минимальными тестами на CRUD.

## 7. Этап 4 — Game API (≈1–1.5 дня)

LLM пока **не подключаем** — эндпоинты возвращают заглушки текста. Цель — проверить механику.

### 7.1 Авторизация

Два способа, оба сводятся к «получить `telegram_id`»:

1. **Бот → API (MVP):** заголовок `X-Internal-Token: <API_INTERNAL_TOKEN>` + `telegram_id` в теле.
   API доверяет боту, потому что оба сервиса наши.
2. **Mini App → API (будущее):** заголовок `X-Telegram-Init-Data` с `initData`,
   API проверяет HMAC-подпись по `BOT_TOKEN` и достаёт `user.id`.

Обе схемы отдают одну и ту же зависимость `get_current_user() -> User`. Второй способ
в MVP можно не реализовывать, но **точку расширения оставить сразу** (`src/api/deps.py`).

### 7.2 Контракты

```
POST /game/start
  body: { telegram_id, intention?: str }
  200:  { game_id, status, position, in_play, turn, guide_message }
  402:  { error: "payment_required", price, pay_url }   # вторая партия

POST /game/{game_id}/intention
  body: { intention: str }
  200:  { game_id, status, guide_message }

POST /game/{game_id}/roll
  200:  { roll, from_position, raw_position, position, transition, event,
          cell: { id, name, theme } | null,
          guide_message, finished, turn, can_roll }

POST /game/{game_id}/respond
  body: { text: str }
  200:  { guide_message, can_roll, safety_flag?: "soft_referral" }

GET  /game/{game_id}
  200:  полное состояние + история ходов (нужно Mini App для отрисовки поля)

POST /game/{game_id}/finish
  200:  { summary, stats }

GET  /users/{telegram_id}/status
  200:  { has_free_game_used, paid_games_available, active_game_id }

POST /payments/tribute/webhook       # см. Этап 8
GET  /health
```

Правила контрактов:

- Никаких Telegram-специфичных полей (`chat_id`, `message_id`) в API. Форматирование — задача клиента.
- `guide_message` — **чистый текст** без Telegram-разметки; бот сам решает, как оформить.
- Идемпотентность `roll`: клиент шлёт `Idempotency-Key` (например `game_id:turn`), чтобы двойной
  тап по кнопке не давал два броска.
- Единый формат ошибок: `{ "error": "code", "message": "..." }`.

### 7.3 Порядок реализации

1. Схемы Pydantic → 2. Репозитории → 3. `game_service` поверх `core/rules` → 4. Роутеры →
5. Интеграционные тесты через `httpx.AsyncClient` на тестовой БД.

**Готово когда:** партию можно пройти целиком через Swagger `/docs`, без бота и без LLM.

## 8. Этап 5 — LLM-оркестрация (≈2–3 дня, бо́льшая часть — тюнинг)

### 8.1 Три вызова, не один

| Вызов | Когда | Что делает | `effort` | `max_tokens` |
|---|---|---|---|---|
| `interpret_cell` | после броска | трактует клетку в контексте запроса и пути, задаёт один вопрос | medium | ~400 |
| `deepen` | на ответ игрока | углубляет, не морализирует, закрывает клетку | medium | ~350 |
| `summarize` | в конце партии | связный инсайт по всему пути | high | ~900 |

Плюс `intro` (представление проводника) и `setup` (уточнение запроса) — их можно сделать
частично статичными текстами: дешевле по токенам и меньше риска для тона на первом контакте.

### 8.2 Сборка запроса (важно для стоимости и кэша)

```python
system = [
    {"type": "text",
     "text": GUIDE_SYSTEM_PROMPT,              # стабильный, ~1–2k токенов
     "cache_control": {"type": "ephemeral"}},
]
messages = [
    # запрос игрока + пройденный путь + фактура текущей клетки
    {"role": "user", "content": build_context_block(game)},
]
```

- `GUIDE_SYSTEM_PROMPT` меняется только при деплое → кэшируется между ходами и между пользователями.
- Контекст партии кладём **после** точки кэша.
- Историю не тащим целиком: передаём компактную выжимку — список пройденных клеток
  (`номер + название`) и по 1–2 ключевых слова из каждого ответа игрока. Полные тексты —
  только за последние 2 хода. Это дешевле и качественнее (меньше шума).
- Проверять `usage.cache_read_input_tokens > 0` начиная со второго хода. Если 0 — искать
  «тихий инвалидатор»: дату/время, несортированный JSON, случайный id внутри системного промпта.

### 8.3 Системный промпт — блоки (`src/llm/prompts.py`, версии в `docs/PROMPTS.md`)

1. **Роль.** Проводник по игре Лила. Не терапевт, не гуру, не астролог. Не ставит диагнозов,
   не предсказывает будущее, не даёт директивных советов.
2. **Тон.** Спокойный, тёплый, на «ты» (решить), без эзотерического пафоса и без канцелярита.
   Не использует штампы вроде «Вселенная посылает тебе».
3. **Метод.** Даёт 2–3 грани трактовки клетки вместо единственно верной. Заканчивает вопросом
   «что из этого откликается?» или конкретным рефлексивным вопросом. Опирается на `facets`
   и `questions` из данных клетки, но переформулирует их под запрос игрока.
4. **Длина.** Жёстко: интерпретация — до 120 слов, углубление — до 90 слов, один вопрос за раз,
   без списков и заголовков (это чат, а не статья). Дублируем ограничение через `max_tokens`.
5. **Связность.** Ссылаться на 1–2 предыдущие клетки, когда это уместно; не пересказывать весь путь.
6. **Границы.** Если в ответе игрока — суицидальные мысли, тяжёлая утрата, признаки насилия,
   острое кризисное состояние: мягко выйти из игровой рамки, назвать происходящее, предложить
   обратиться к специалисту, не продолжать интерпретацию как ни в чём не бывало.
7. **Анти-паттерны** (явный список): не хвалить ответ игрока дежурными фразами, не начинать
   с «Отличный вопрос», не пересказывать сказанное игроком его же словами, не выдавать
   нумерованных планов действий.

### 8.4 Safety-слой (`src/llm/safety.py`)

Двухуровнево:

1. Быстрый лексический прескрин ответа игрока по списку маркеров → если сработал,
   в промпт добавляется явная инструкция режима поддержки.
2. Инструкция в системном промпте (блок 6) как основной механизм.

Ответ API помечается `safety_flag`, бот показывает контакты помощи из `texts.py`.
Партия при этом **не ломается**: игрок может продолжить или завершить.

### 8.5 Надёжность

- Таймаут на вызов LLM (30–45 с), ретраи делает SDK; при финальном провале — заготовленный
  фолбэк-текст («Проводник задумался, попробуй ещё раз»).
- Ошибка LLM **не должна** терять бросок: сначала пишем `move` в БД, потом зовём LLM;
  на повторный запрос отдаём интерпретацию для уже сделанного хода.
- Логируем токены каждого вызова в `messages` → через неделю видно реальную себестоимость партии.

### 8.6 Оценка стоимости партии (прикинуть до запуска)

Ориентир на партию в 25 ходов: ~50 вызовов LLM, вход 2–4k токенов (в основном из кэша),
выход ~300 токенов. Точную цифру считаем после первых 3 тестовых партий по данным из `messages` —
от неё зависит цена второй партии.

**Готово когда:** через `scripts/play_cli.py` проходит полная партия с реальными ответами LLM,
тон устраивает эксперта, длина ответов в заданных границах.

## 9. Этап 6 — Telegram-бот (≈1–1.5 дня)

Тонкий клиент. Никакой логики.

### 9.1 Сценарии

| Шаг | UI |
|---|---|
| `/start` | приветствие проводника + кнопка «Начать партию» |
| Настройка | вопрос про запрос игрока → бот ждёт текст (FSM-состояние `waiting_intention`) |
| Ход | кнопка «Бросить кубик» → сообщение с результатом броска и интерпретацией |
| Ответ | игрок пишет текст → бот шлёт в `/respond` → углубление + кнопка «Следующий бросок» |
| Пропуск | кнопка «Пропустить» — можно не отвечать на вопрос клетки |
| Финиш | сообщение о завершении + резюме + вопрос обратной связи |
| Вторая партия | `/start` → 402 от API → сообщение с ценой и кнопкой оплаты |

### 9.2 Детали, которые обычно забывают

- **«Печатает…»**: `bot.send_chat_action(chat_id, "typing")` в цикле, пока идёт вызов LLM.
  LLM отвечает 5–15 с; без индикатора это выглядит как зависание.
- **Защита от двойного тапа**: сразу после нажатия убирать инлайн-клавиатуру
  (`edit_reply_markup(None)`) + `Idempotency-Key` на стороне API.
- **Длинные ответы игрока**: лимит Telegram 4096 символов; обрезать до ~1500 перед отправкой в API.
- **Визуализация броска**: можно слать нативный `send_dice` и использовать его значение — но тогда
  бросок делает Telegram, а не наш движок. **Решение для MVP: бросает сервер**, `send_dice`
  не используем (иначе разъедется логика и Mini App). Вместо этого — эмодзи-строка с числом.
- **Прогресс**: в каждом сообщении хода писать «Клетка 34 — Название · ход 12 из 40».
- Все статические тексты — в `texts.py`, чтобы правились без вычитывания кода.

**Готово когда:** партия целиком проходится в Telegram на локальном polling.

## 10. Этап 7 — Тестовые партии и тюнинг тона (≈2 дня, растянуто)

1. Прогнать 3–5 полных партий (сам + эксперт + 1–2 доброжелательных тестера).
2. После каждой партии выгружать `messages` в markdown (`scripts/export_game.py`) и вычитывать.
3. Вести `docs/PROMPTS.md`: что поменяли в промпте, почему, что улучшилось.
4. Отдельно проверить **краевые случаи тона**:
   - игрок отвечает односложно («не знаю», «ок»);
   - игрок отвечает агрессивно или троллит;
   - игрок пишет тяжёлое (проверка safety-ветки на тестовых данных);
   - игрок задаёт встречный вопрос вместо ответа («а что это значит?»);
   - игрок пишет не по теме.
5. Зафиксировать 5–7 «эталонных» ответов проводника как регресс-набор: после каждой правки
   промпта прогонять их и сравнивать глазами.

**Готово когда:** эксперт говорит «да, так можно показывать людям».

## 11. Этап 8 — Монетизация через Tribute (≈0.5–1 день)

### 11.1 Логика

1. `POST /game/start`:
   - `has_free_game_used == false` → создаём партию; флаг ставим в `true` **при завершении**
     первой партии, а не при старте (иначе брошенная на первом ходу партия сожжёт бесплатную);
   - иначе `paid_games_available > 0` → декремент, создаём партию с `is_paid=true`;
   - иначе → `402` + `price` + `pay_url`.
2. Бот показывает сообщение с ценой и кнопкой-ссылкой на Tribute.
3. Tribute шлёт вебхук на `POST /payments/tribute/webhook`.
4. API проверяет подпись → пишет `payments` (идемпотентно по `external_id`) →
   `paid_games_available += 1` → отправляет пользователю сообщение «оплата прошла, можно начинать».

### 11.2 Обязательные детали

- **Проверка подписи вебхука** по `TRIBUTE_WEBHOOK_SECRET`. Без неё любой желающий выдаст себе партии.
- **Идемпотентность**: повторная доставка того же вебхука не должна начислять вторую партию
  (`external_id` unique).
- **Связка платежа с пользователем**: прокидывать `telegram_id` в payload/ссылку оплаты.
- **Ручной фолбэк**: админ-команда `/grant <telegram_id>` (только для своих ID) — на случай,
  когда вебхук не дошёл, а человек заплатил. Обязательна для первого месяца.
- Логировать сырой payload в `payments.raw_payload` — при спорах это единственное доказательство.

> Точные форматы вебхука и ссылки оплаты берутся из актуальной документации Tribute на момент
> реализации; здесь фиксируется только наша сторона контракта.

**Готово когда:** тестовый платёж проходит end-to-end, повторная доставка вебхука не даёт дубля.

## 12. Этап 9 — Метрики (≈0.5 дня)

Таблица `events`, минимальный набор:

| Событие | Когда |
|---|---|
| `game_started` | старт партии (props: `is_paid`) |
| `intention_set` | игрок сформулировал запрос |
| `move_made` | каждый бросок (props: `turn`, `position`, `transition`) |
| `player_responded` | ответ игрока (props: `char_len`, `word_count`) |
| `response_skipped` | нажал «Пропустить» |
| `game_finished` | завершение (props: `reason` = `enlightenment` / `turn_limit`) |
| `game_abandoned` | нет активности 48 ч (крон-джоб) |
| `paywall_shown` / `payment_succeeded` | воронка оплаты |
| `feedback_given` | ответ на финальный вопрос |
| `safety_triggered` | сработал safety-слой |

Отчёт — один SQL-скрипт `scripts/metrics.sql`, выдающий 4 метрики MVP: процент завершивших
от начавших, конверсия во вторую партию, средняя длина ответа игрока, распределение причин
завершения. Дашборд в MVP не нужен.

## 13. Этап 10 — Деплой (≈0.5 дня)

Railway, три компонента:

1. `postgres` — управляемый.
2. `api` — `uvicorn src.api.main:app --host 0.0.0.0 --port $PORT`, healthcheck `/health`.
3. `bot` — отдельный сервис, `python -m src.bot.main`.

Решения:

- **Бот в MVP — polling**, не webhook: проще, надёжнее при редеплоях, нагрузки нет.
  Webhook — когда появится Mini App или заметный трафик.
- Alembic-миграции — в release-команде сервиса `api`, не в рантайме бота.
- Один `Dockerfile` на оба сервиса, разные `CMD`.
- Секреты — только в переменных окружения Railway; `.env` в репозиторий не коммитим.
- Логи structlog в stdout → Railway logs. Отдельно завести алерт (хотя бы себе в Telegram)
  на исключения в `api`.
- Ежедневный бэкап Postgres (плагин Railway или `pg_dump` по крону) — партии людей терять нельзя.

## 14. Этап 11 — Мягкий запуск

1. 5–10 «своих» пользователей → собрать обратную связь по тону, а не по багам.
2. Правки промпта и текстов (не кода).
3. Публикация в канале: один пост с описанием игры + ссылка на бота.
4. Первую неделю читать выгрузки партий каждый день. Это единственный способ понять,
   где проводник фальшивит.
5. Через 2 недели свести метрики и решить: улучшать конверсию, делать Mini App
   или делать тематические версии игры.

## 15. Что осознанно НЕ делаем в MVP

- Mini App (только архитектурная готовность: Game API + состояние в Postgres + место под `initData`-auth).
- Тематические версии игры (денежная и т. д.).
- Продолжение партии между сессиями как фичу. Технически партия и так живёт в БД, но UX
  «вернуться к незаконченной партии» не проектируем: при `/start` с активной партией просто
  предлагаем продолжить или завершить.
- Групповые и парные форматы, голосовой ввод, реферальную программу, подписку.

## 17. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Тон LLM «не тот», продукт ощущается дёшево | высокая | не сокращать Этап 7; регресс-набор ответов; фактура клеток вычитана вручную |
| Партия слишком длинная, люди не доходят до конца | высокая | симуляция на Этапе 5.4; лимит ходов; возможность завершить досрочно с резюме |
| Себестоимость партии выше цены | средняя | prompt caching, компактный контекст, `effort=medium`, замер после 3 партий |
| Вебхук Tribute не доходит | средняя | идемпотентность + ручная команда `/grant` |
| Игрок в тяжёлом состоянии | низкая, но критичная по последствиям | двухуровневый safety-слой, явные контакты помощи, дисклеймер при старте |
| Логика расползлась в хендлеры бота | средняя | правило код-ревью «хендлер не знает про игру»; бот ходит в API только через `api_client.py` |
